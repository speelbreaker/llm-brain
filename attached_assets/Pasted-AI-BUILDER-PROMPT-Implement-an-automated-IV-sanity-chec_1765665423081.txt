AI BUILDER PROMPT

Implement an automated “IV sanity check” and expose it via health APIs so my environment bot can call a single endpoint.

Goal

I want a small, fast health check that proves the IV calibration pipeline is actually wired:

Calibration → IV multiplier → synthetic prices → selector decisions

It should:

Run two tiny backtests for each of:

the generic covered call selector

the GregBot – VRP Harvester selector

Compare low vs high IV multiplier behavior.

Return a compact JSON summary with an overall status = ok | degraded | failed.

Plug into:

the existing healthcheck module

the System Controls & Health UI

a new /api/health/iv_sanity endpoint (for the Telegram env-bot).

Use whatever internal backtest manager / state builder we already have; do not shell out or hit HTTP from this script.

“Greg” selector: use the selector backing the “GregBot – VRP Harvester” row in the Selector Frequency Scan UI.

IV multiplier scenarios

For each selector, run two backtests with:

Common fields: config above, sigma_mode="rv_x_multiplier".

IV multipliers:

Generic covered call

Low IV: synthetic_iv_multiplier = 0.8

High IV: synthetic_iv_multiplier = 1.2

GregBot VRP Harvester

Low IV: synthetic_iv_multiplier = 0.9

High IV: synthetic_iv_multiplier = 1.1

Use the normal backtest pipeline (same as the Backtesting Lab) but with a very small date window as above so this runs fast.

For each backtest, extract at least:

num_trades

net_profit_pct

sharpe_ratio (if available)

optionally win_rate / avg_trade_usd (nice to have for the JSON).

Pass / fail logic

Implement simple, deterministic rules:

Generic covered call

Expectation: high IV should give more trading opportunity and/or better net PnL.

Mark selector status = "failed" if both:

num_trades_low == num_trades_high

abs(net_profit_pct_high - net_profit_pct_low) < 0.5

Otherwise status = "ok".

GregBot – VRP Harvester

Expectation: high IV should usually unlock more trades and/or higher net PnL.

Mark selector status = "failed" if:

num_trades_high <= num_trades_low

and net_profit_pct_high <= net_profit_pct_low + 0.5

Otherwise status = "ok".

The top-level run_iv_sanity_check() should return a JSON-serializable dict:

{
    "status": "ok" | "degraded" | "failed",
    "summary": "Short human summary sentence",
    "selectors": [
        {
            "selector": "...",
            "iv_low": 0.9,
            "iv_high": 1.1,
            "status": "ok",
            "reason": "High IV produced more trades and higher PnL.",
            "low":  { "num_trades": ..., "net_profit_pct": ..., "sharpe_ratio": ... },
            "high": { "num_trades": ..., "net_profit_pct": ..., "sharpe_ratio": ... }
        },
        ...
    ],
}


Overall status logic:

If all selectors are "ok" → status = "ok".

If at least one "failed" → status = "failed".

Otherwise (e.g. one ok, one borderline) → status = "degraded".

Make sure errors (no data, exceptions) are caught and returned as status="failed" with a clear reason.

Example (pseudo-code – adapt to the existing patterns):

def check_iv_sanity() -> HealthCheckResult:
    payload = iv_sanity_check.run_iv_sanity_check()
    status = payload.get("status", "failed")

        severity=severity,

    )
