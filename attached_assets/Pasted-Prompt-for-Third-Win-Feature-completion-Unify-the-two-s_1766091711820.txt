Copy/paste this as a one-shot “AI builder” prompt.

Goal
Unify our two synthetic-vol engines into a single canonical “Synthetic Vol Model” used everywhere (backtests, scoring, selector scans, and any synthetic/hybrid pricing). This reduces duplicated logic, inconsistent multipliers, and drift between “synthetic skew engine” vs “vol surface/regime engine”.

Non‑Negotiables
Single source of truth: After this change, there should be one canonical engine that answers “what IV do we use for this option at time 
t
t?” (including ATM term structure + skew/smile).
No behavior regressions without explicit intent: Default historical backtests must remain protected from look-ahead (i.e., no live skew leakage).
UI alignment requirement (IMPORTANT): Any changes to code functionality or new configuration knobs must be reflected in the UI wherever applicable (and the API contracts backing that UI).
Current Problem (what to unify)
We currently have overlapping synthetic-vol logic split across:

A “vol surface / calibration-config” pathway (multipliers, DTE bands, skew anchors)
A “synthetic skew engine” pathway (skew factors with source controls, time-awareness)
Optional regime dynamics for IV/skew evolution
These overlap in responsibility and can disagree (especially around: multiplier application order, DTE handling, and skew anchoring).

Target Design (what “unified” means)
Create a single module (suggestion: src/synthetic/engine.py) implementing a stable API like:

SyntheticVolEngine.get_iv(underlying, as_of, dte_days, abs_delta, option_type, *, mode) → iv
SyntheticVolEngine.get_atm_iv(underlying, as_of, dte_days, *, mode) → atm_iv
SyntheticVolEngine.get_skew_anchor_ratio(underlying, as_of, dte_days, abs_delta, option_type, *, mode) → ratio
mode (or config) must support:
Surface source: runtime surface config (calibration-driven) vs none
Skew source: none/harvested/live (but historical backtests must never use live)
Internally, the engine should:

Compute/select base ATM vol (RV/ATM IV/mark IV selection depending on existing sigma_mode semantics).
Apply calibration multipliers consistently (global + DTE band).
Apply skew/smile consistently:
Prefer calibrated skew anchors when configured and DTE in range
Otherwise apply skew source fallback (harvested/live/none) with as_of enforced
(Optional) apply regime evolution as a wrapper, but still through the same interface.
Refactor Steps (implementation)
Introduce SyntheticVolEngine and move all “compose IV” logic into it.
Update call sites to use the engine:
Pricing entrypoints (sigma selection / IV with skew)
State building (synthetic candidates, hybrid candidates)

Reduce old modules to thin wrappers or delete them:
Keep backwards-compatible function names if widely referenced, but route them into SyntheticVolEngine.

base_iv → multiplier → skew
Enforce “no look-ahead” at the boundary:
If as_of is historical and caller requests live, error or hard-fallback to safe source (choose one and document it).
